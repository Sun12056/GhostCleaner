# 修复「开发项目」误判：48 条里 23 条被判成开发项目

> 日期：2026-10-17
> 结论：**已修复并保留**。代价是指标变差（FP 2→4），但那是暴露真问题，不是制造新问题。

---

## 1. Bug

`DirectoryFactsDetector`：

```csharp
bool isDev = devFiles.Count > 0 || devDirs.Count > 0;   // 命中 1 个特征即判"开发项目"
```

两个因素叠加放大了它：

1. `dirNames` 纳入了**递归子目录**（`TopLevelDirectoryNames.Concat(AllDirectoryNames)`）
2. `DevDirectoryIndicators` 含 `sdk` / `ndk` / `jdk` / `jre` / `env` / `vendor` /
   `obj` / `target` / `packages` / `venv` 等**弱特征** —— 它们在普通软件里同样常见

结果：**任何大目录都能凑够特征。**

---

## 2. 实测影响

48 条里 **23 条（48%）** 被判成"开发项目"：

```
bilibili、瓜子影视、桌面、文档、下载、QuarkCloudDrive、DeepSeek、
CodeBuddy CN、aDrive、Folia、HECATE Connect、inkstone、keke …
```

6 条真残留里 **3 条**（QClaw、微信web开发者工具、bilibili）被判成开发项目并受保护。

---

## 3. 修法：非对称 + 强弱分离

**关键：两处的错误代价完全不同，不能用同一个判据。**

| 用途 | 判据 | 理由 |
|---|---|---|
| 分类 / 减分 | **顶层 + 强特征** | 误标成"开发项目"是 Core 在胡说，属证据失真 |
| 保护 `IsProtected` | **顶层+递归 + 强弱全部，≥1** | 宁可多保护，**绝不因修 bug 削弱安全网** |

- **强特征**（开发项目特有）：`.git` `.svn` `.hg` `node_modules` `.idea` `.vscode`
  `.gradle` `.mvn`，以及全部 `DevFileIndicators`
- **弱特征**（普通软件也有）：`sdk` `ndk` `jdk` `jre` `env` `vendor` `obj`
  `target` `packages` `venv` `site-packages` `conda` …

新增 `Heuristics.DevStrongDirectoryIndicators` 与
`MatchesDevStrongDirectoryIndicator`。

> 修分类的 bug 不能顺带把更多目录变得可删除 —— 这点在代码注释里写死了。

---

## 4. 验证

| 指标 | 改前 | 改后 |
|---|---|---|
| 判为"开发项目" | 23 | **1**（`node.js`，确实是工具链 ✅） |
| 受保护数量 | 27 | **27** |
| **失去保护的目录** | — | **0** ✅ |
| 桌面 / 文档 / 下载 类别 | 开发项目 | **用户数据**（仍受保护） |

测试 134 通过。

---

## 5. ⚠️ 代价：FP 从 2 涨到 4

非管理员口径（阈值 40）：

```
改前: TP=0 FP=2 TN=33 FN=6
改后: TP=0 FP=4 TN=31 FN=6
```

新增的两条：

```
IROK Software       置信 24 → 65   （原被判"开发项目"而减分）
Microsoft VS Code   置信 12 → 62   （同上）
```

两条真值**都是"在用"**。

### 这是「暴露」不是「制造」

它们原本的低分（24、12）**建立在错误的分类之上** —— 因为被误判为开发项目才被减分。
修复后回到 65、62，反映的是**真实的**「缺失系统关联」证据。

> **分数变高了，但不是变坏了 —— 是变诚实了。**

而"诚实的高分"恰好暴露了根因：分数本来就不可靠（缺失系统关联是重装造成的）。
这与 Core 0.2 定案（**不做自动判定**）完全一致 ——
它又一次证明**不能拿这个分数当结论**。

---

## 6. 为什么保留这个改动

- 收益：分类 23 → 1，用户不再看到「bilibili 是开发项目」这类胡说
- 安全网零削弱（27 → 27，无一条失去保护）
- 代价是**暴露真问题**，不是制造新问题

**掩盖不是解决方案。** 靠一个 bug 把 FP 压下去，指标好看但证据是假的 ——
而 Core 0.2 的全部价值就在于证据可信。

---

## 7. 遗留

- 现有测试未覆盖该场景（134 通过但无新增）—— 本次靠实测数据验证，
  后续应补一个"只有弱特征的目录不得判为开发项目"的契约测试。

---

## 8. 与 v0.2 的关系

本次修复**不改变** Core 不做自动判定的定案，反而给它提供了又一个佐证：
把误判修掉之后，分数对在用软件照样给出高分（IROK 65 / VS Code 62），
说明问题不在某个判据，而在**单次快照这个维度本身**。
