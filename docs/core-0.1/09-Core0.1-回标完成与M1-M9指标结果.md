## 4. 核心结论

### 4.1 安全指标全达标，有效性指标全崩

> **M1–M9 全部为 0：不会误删。**
> **Precision 0.29 / Recall 0.33：也基本没用。**

与 `05-…第一轮验证` 中「可用性接近归零」的推断一致，现在有回标数据支撑：
7 条被判为「疑似残留」的样本里 5 条是误报；6 条真残留里 4 条根本没识别出来。

### 4.2（最重要）置信度与真值呈**负相关**

| 分组 | 置信度 |
|---|---|
| 真值 = 残留（6 条） | 100, 73, **0, 0, 0, 0** — 4 条触底 |
| 真值 = 在用的高分段（5 条） | 100, 100, 68, 56, 48 |

**置信度越高，越可能是「仍在使用的软件」，而不是残留。**

这直接挑战 v0.1 的核心假设：

```
原假设：完整软件特征（卸载器/版本资源/厂商）+ 缺失系统关联 = 残留
实测：  完整软件特征 + 缺失系统关联 = 重装后仍在使用的软件
```

原因可由用户说明解释：本机重装过系统，D 盘留下的正是**正规安装的软件目录**，
重装后注册表登记丢失（→ 缺失关联 +20 等全额计入），但软件更新后继续在用。
而真正的残留（`QClaw`、`Program Files\bilibili` 等）反而是**残缺目录**，
软件特征弱 → 置信度低 → 被判 0 分。

即 §3 中 `MissingUninstallEntry` 在重装场景失去区分度的判断，已被回标数据证实。

### 4.3 改动 3 的潜在副作用（需警惕）

`D:\DriverGenius` 真值 = 残留，但 90 天内 **351 个文件被修改**
（卸载后残留的后台服务仍在写日志）。改动 3 会给它 `RecentFileActivity(−25)`。

本例中它原本已是 0 分、无进一步恶化空间，但**方向上存在隐患**：
「仍在写文件」不等于「仍在使用」，对卸载后残留的常驻服务会误判为在用。
回标数据中仅此 1 例，暂不足以调整，需在更大样本上观察。

## 5.2 召回低的根因：`isDev` 判据 bug

`DirectoryFactsDetector.cs:48-50`：

```csharp
var devFiles = fileNames.Where(Heuristics.MatchesDevFileIndicator).ToList();
var devDirs  = dirNames.Where(Heuristics.MatchesDevDirectoryIndicator).ToList();
bool isDev = devFiles.Count > 0 || devDirs.Count > 0;   // ← 命中 1 个即判"开发项目"
```

命中**一个**特征就判为开发项目 → `DevelopmentProject −50`。

4 条真残留（FN）中 **3 条**因此被压到 0 分：

| 样本 | 类别 | 关键负向 |
|---|---|---|
| `D:\QClaw` | 开发项目 | `DevelopmentProject−50` `PortableSoftware−45` `Configuration−30` `UserData−30` `RecentFileActivity−25` |
| `D:\微信web开发者工具` | 开发项目 | `Shortcut−60` `DevelopmentProject−50` `PortableSoftware−45` … |
| `D:\Program Files\bilibili` | 开发项目 | `DevelopmentProject−50` `UserData−30` `SystemDirectory−30` |

且存在**逻辑矛盾**：`QClaw` 命中 `Uninstaller+25`（自带卸载器），
却被同时判为「绿色软件」（其结构判据本要求 `!HasUninstaller`）。

这解释了 `06-…md` 中「开发项目 22/47 = 47% 比例偏高」的疑问 ——
**Electron 应用的目录结构（`resources` / `locales` / `.js` / `package.json`）与开发项目判据重叠**。

## 5.3 ⚠️ 但**不能现在修** `isDev`：会让 Precision 崩盘

被判为「开发项目」的 22 条，真值分布：

| 真值 | 条数 |
|---|---|
| **在用** | **15** |
| 残留 | 3 |
| 不确定 | 4 |

若去掉 `−50`，这 15 条「在用」的分数**集体 +50**，绝大多数会越过 40 阈值：

| | 现在 | 修 `isDev` 后（估算） |
|---|---|---|
| FP | 4 | **≈ 19** |
| TP | 2 | ≈ 3 |
| `Precision` | 0.333 | **≈ 0.14** |

> **关键洞察**：`isDev` 判据本身是错的，但它产生的 `−50`
> **误打误撞地掩盖了 FP 问题**（把大量在用的软件压到了 0 分）。
>
> 在修掉 FP 的真正根因之前修它，会让 Precision 从 0.333 崩到约 0.14。
> **修复顺序不能反。**
