## 1. 为什么是跨时间观测

Core 0.2 已定案「只提供证据，不做自动判定」—— 单次快照无法区分
「重装后继续用」与「真废弃」（五个候选信号源全部证伪，见 `14-…定案.md`）。

唯一可能有解的方向是**跨时间观测**：多次扫描比对**趋势**，而非单次快照。

其中 **「最后写入时间前移」强于任何"运行过"类信号** ——
卸载动作不会让目录产生新写入，所以只要有新写入，就说明有人在用它。

### 2.1 JSONL 新增 `Snapshot` 区块

此前 `ScanRecord` 完全没有体积 / 时间字段，无从比对。已补：

```json
"snapshot": {
  "sizeBytes": 881234567,
```

## 3. 当场印证：通用 exe 名的真实规模

导出 `mainExecutables` 后立刻能看到问题（Weixin 目录里就有
`crashpad_handler.exe`、`Uninstall.exe`）。量化如下（48 条快照，145 个 exe 名）：

| | 数量 | 占比 |
|---|---|---|
| exe 名总数 | 145 | 100% |
| **跨检出目录重名的** | **31** | **21.4%** |
| 其中黑名单（卸载器 / 公共运行时）能覆盖 | **4** | **13%** |
| **只能靠「跨目录重名」抓到的** | **27** | — |

黑名单漏掉的（按出现目录数排序）：

```
elevate.exe          7 个目录    ← 黑名单不可能预先想到
rg.exe               5 个目录    ← ripgrep，多软件自带
node.exe             5 个目录
esbuild.exe          4 个目录
clipboard_x86_64.exe 3 个目录
singlefilehost.exe   3 个目录
ffmpeg.exe           3 个目录
```

### 结论

**UI 提的第 3 条约束（同一 exe 名出现在 ≥2 个检出目录 ⇒ 不产出候选）是主约束，
第 1、2 条（黑名单）只能覆盖 13%。**

`elevate.exe` 跨 7 个目录 —— 这类名字不可能预先写进黑名单，
只有数据驱动规则能抓到。这也印证了"黑名单的定义就是已知过期名单"。

## 6. 与补样本的关系

补样本（换非重装环境的机器）与本方向**不冲突、可并行**：

| | 作用 | 谁推进 |
|---|---|---|
| 补样本 | 解决"正类只有 6 条"的统计弱点 | 需换机器（用户决策） |
| 跨时间观测 | 换一个维度（时间）找区分能力 | 本轮已启动，靠时间累积 |

前者修的是**当前指标的置信度**，后者找的是**新的区分维度**。
