# Core 0.2 定案：Core 不再做自动判定

> 日期：2026-10-17
> 依据：47 条人工回标 + 5 个候选信号源的完整调研
> 状态：**自动判定目标放弃**，定位调整为「只提供证据」

---

## 0. 一句话结论

**五个信号源全部失败，无一达到 `AUC ≥ 0.8` 的落地门槛。**
目录内信息不足以区分「重装后继续用」与「真废弃」—— 两者特征几乎完全一致。

Core 0.2 不再追求自动判定，改为：**只提供证据，把判断交还用户。**

---

## 1. 五个信号源汇总（终结）

| # | 信号源 | 可用性 | AUC | 判定 |
|---|---|---|---|---|
| 1 | AppData（目录名 / exe 厂商） | 14/47 · 19/47 | **0.327** | ❌ 反向，比随机还差 |
| 2 | UserAssist | **0 条目** | — | ❌ 本机被清空 |
| 3 | Recent | 覆盖 4 个目录 | 0.571 | ❌ 只记文档不记程序 |
| 4 | 重装场景检测 | 21/41 属重装前 | 无区分 | ❌ 降权会 TP/FP 齐降 |
| 5 | **Prefetch** | 35/41 命中 | **0.657 / 0.620** | ❌ 与现有持平 |

**参照：当前置信度 AUC = 0.648。**

> 门槛是我自己在调研前定的：`AUC ≥ 0.8` 才落地，`< 0.65` 不值得。
> Prefetch 是唯一逼近门槛的，但排除误匹配后 **0.620 < 0.65**。

## 2. Prefetch 详细（本次实测）

### 2.1 原始结果

```
Prefetch 文件数: 301    去重后 exe 名: 198
总命中: 35 / 41
分组：在用 25/35 有记录(71%)   残留 4/6 有记录(67%)
```

**67% vs 71% —— 没有区分度。**

### 2.2 AUC

| 口径 | AUC |
|---|---|
| 全部命中照算 | 0.657 |
| **排除通用 exe 名后** | **0.620** |
| 现有置信度（参照） | 0.648 |

排除误匹配后，**比现有置信度还差**。

### 2.3 决定性反例

```
Registry Repair   真值=残留  置信=96  Prefetch=2026-10-16（昨天）
QClaw             真值=残留  置信=0   Prefetch=2026-09-22
bilibili          真值=残留  置信=0   Prefetch=2026-09-06
```

**`Registry Repair` 是回标里置信度最高的真残留（96 分，判对），
但 Prefetch 显示它昨天还运行过。**

若落地「近期运行过 = 在用」，这条会被判为在用 ——
**把我们唯一的 96 分 TP 打掉，Recall 从 0.333 掉到 0.167。**

> 这印证了 UI 的预警：废弃软件在重装前跑过，也会留记录。
> 更一般地说：**"近期运行过" ≠ "在用"**（用户可能只是打开看了一眼）。

## 3. 通用 exe 名误匹配（本次新发现，值得记住）

**11 / 41 条命中的是通用名：**

| exe 名 | 误匹配到的目录 |
|---|---|
| `UNINSTALL.EXE` | wangyiyunyinyue、IROK Software、aDrive、CloudMusic、ZWCAD2026（5 个） |
| `NODE.EXE` | node.js、微信web开发者工具 |
| 其它 | `UNINS000`、`CHROME`、`MEDIA_PLAYER`、`LOGUPLOAD` |

Prefetch 文件名是 `<EXENAME>-<hash>.pf`，**hash 由 exe 完整路径算出**，
正是用来区分同名不同路径的。按名字匹配必然跨目录误匹配。

要精确就得解析 `.pf` 的 hash（SCCA 格式，成本高、且算法未公开稳定）。

> **教训（对未来任何信号都适用）**：
> 任何基于 exe 名匹配的信号，都必须处理「同名不同路径」，
> 否则命中率看着很高（35/41），实际是假的。
> **本次就是靠"命中率 85%"这个数字差点被误导。**

## 4. 定案：Core 的定位

| | 之前 | 现在 |
|---|---|---|
| 目标 | 自动判定"是不是残留" | **只提供证据** |
| 输出 | 置信度 = 残留概率 | 置信度 = **使用迹象的缺失程度** |
| 建议 | 可输出 `Quarantine` | **永不输出**（已落地，建议集收敛为 `{Keep, Review, HighRiskReview}`） |
| 措辞 | "非常高概率残留" | "**未检测到任何使用迹象**"（已落地 + 测试锁死） |
| 判断权 | Core | **用户** |

**这不是退让，是诚实。** 在 `Precision 0.333` 下，由 Core 建议"可清理"本身就是误删风险源。

---

## 5. 仍然有价值、已落地的能力

| 能力 | 状态 |
|---|---|
| 安全指标 M1–M9 | **全 0**（只读、无副作用、受保护目录不碰） |
| 结构化警告 | 7 类 code + `IsUncertainty` 分区 |
| 自带卸载器提示 | 引导用卸载器而非删除（比删除安全） |
| 重装场景提示 | 说明"这条判定为什么不可信" |
| 文件活动量级 | `RecentModifiedFileCount90/365`，给量级不给布尔 |
| 确定性保护 | 受保护路径、运行中进程、只读扫描 |

这些都不依赖"判定准确"，**在准确率低的前提下依然成立**。

## 6. 后续方向

| 项 | 说明 |
|---|---|
| **v0.2 跨时间观测** | 唯一可能有解的方向：多次扫描比对**趋势**，而非单次快照 |
| **补样本** | 当前正类仅 6 条。最有效的补法是**换一台非重装环境的机器**（本机是 `MissingUninstallEntry` 完全失效的极端情形） |
| **`isDev` 判据 bug** | 已知但**不修** —— 那个 −50 误打误撞掩盖了 FP 问题，修了会让 Precision 从 0.333 崩到约 0.14。须先解决 FP 根因 |
| **阈值 0.10 / 权重** | 需更多样本才能校准，当前数值不可信 |

## 7. 给未来的自己

**不要再重复以下调研**（已证伪，见 `11-…新信号调研.md` 与本文档）：

- ❌ AppData 目录名 / 厂商匹配（厂商级会把残留与在用绑成同一值）
- ❌ UserAssist（目标用户恰恰会清空它）
- ❌ Recent（记文档不记程序）
- ❌ 重装场景检测（无区分能力，只能用于提示）
- ❌ Prefetch（与现有持平，且真残留也有近期记录）

若将来要再找信号，先问一句：
**"这个信号能不能把 `Registry Repair`（残留但昨天运行过）和 `wangyiyunyinyue`（在用但目录内零活动）分开？"**
分不开就不用往下做了 —— 这两个样本就是当前的判据基准。
