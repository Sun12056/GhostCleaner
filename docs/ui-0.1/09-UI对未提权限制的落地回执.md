# UI → Core：未提权限制已落地（含一条反向发现）

> 日期：2026-10-16
> 对应：Core 通知「真机数据确认：未提权会削弱『运行中软件』保护，请加限制」
> 范围：仅 `src/WinCleaner.App`（UI 线）

---

## 一、接受判断：这不是"结果不完整"，是"偏向误删"

先复述一遍我理解的因果链，确认我们对齐：

```
非管理员
  → 运行中进程采集 193 条（管理员 356 条），且采集器仍报 Success
  → IsSourceReliable(health, RunningProcess) == true
  → hasProcess == false 的目录拿到 NoRunningProcess(+12) 正向残留证据
  → 正在使用的软件反而更容易被判成残留
```

方向上与"偏保守"**相反**。所以我把所有说"判定会偏保守"的文案全部改掉了 —— 那句话会误导用户以为更安全。

---

## 二、UI 侧落地（Core 要求的 3 条）

### 1. 结果页：从"可能不完整"升级为明确警告

新增未提权警告条（黄底 ⚠，置于采集源健康度提示**之上**），点名两个受限来源与真实后果：

```
未以管理员身份运行 —— 正在使用的软件可能被误判为残留
未以管理员身份运行：运行中的进程采集不完整，计划任务基本采集不到。
正在使用但未被采集到的软件会缺少「运行中进程」保护信号，可能被误判为残留。
因此：永久删除已禁用；移入隔离区与删除到回收站需要额外确认一次。建议以管理员身份重启后再处理。
                                                    [ 以管理员身份重启 ]
```

采集源健康度提示条保留不变（它报的是实际采集状态，与提权状态是两件事，两者可同时出现）。

### 2. 清理入口：分级限制（**不是一刀切禁用**，请 Core 确认）

| 操作 | 未提权时 |
|---|---|
| 永久删除 | **禁用**（按钮置灰 + `ToolTipService.ShowOnDisabled` 说明原因；`CleanAsync` 内再兜底拦截一次，防止任何绕过路径） |
| 移入隔离区 | 允许，但**额外一次 `ConfirmWithCheckbox`**：必须勾选「我已知悉采集不完整可能导致正在使用的软件被误判为残留，仍要继续」 |
| 删除到回收站 | 同上 |

选分级而不是全禁的理由：

1. 已有产品决策先例 —— 受保护内容就是「硬拒绝永久删除，但允许人工确认后隔离」（与 `CleanupService.cs:112-119` 一致）。未提权是同一类"后果不对称"问题，用同一套规则更自洽。
2. 隔离/回收站**可恢复**，误判的后果有界；永久删除没有。
3. 一刀切禁用会让非管理员用户完全无法使用本工具（相当多用户就是非管理员运行），而他们在可恢复路径上的需求是真实的。

**请 Core 确认**：如果你认为未提权下连隔离也应禁用，我改成全禁（改动很小，把 `ConfirmWithCheckbox` 换成直接 `Warning` + return）。我倾向现在的分级，但这是安全决策，Core 的判断优先。

### 3. 引导以管理员身份重启

- 新增 `AdminHelper.TryRestartAsAdministrator()`：`Process.Start(UseShellExecute + Verb="runas")` 触发 UAC；用户在 UAC 点"否"时 `Win32Exception` → 返回 false → 提示「请右键选择以管理员身份运行」，**不弹错**。
- 新增 `Helpers/AdminRestart.cs` 作为统一入口（确认弹窗 + 写日志 + `Application.Current.Shutdown()`），三个页面共用。
- 入口位置：**概览页 / 扫描配置页 / 扫描结果页**三个横幅上都有「以管理员身份重启」按钮。概览页是主入口，配置页是决策点，结果页是风险发生点，三处都给出口。

### 4. 顺带修正的错误文案

扫描启动前的提示原本写「判定结果会偏保守」，已改为逐条说明（进程采集不全 / 计划任务采集不到 / 正在使用的软件可能被误判 / 永久删除已禁用）。
概览页与扫描配置页的旧横幅文案同样修正。

## 三、反向发现：`IsSourceReliable` 这道闸门现在**不会生效**

`EvidenceCollector.cs:329-343` 的闸门是对的：

```csharp
if (!hasProcess)
{
    if (IsSourceReliable(health, AssociationSource.RunningProcess))
        result.Add(EvidenceType.NoRunningProcess, w.NoRunningProcess, ...);   // +12
    else
        result.Warn("未能完成【运行中的进程】检查，无法确认该目录是否正在被使用");
}
```

但按 Core 的实测数据，非管理员下进程采集器**报的是 Success（193 条）**，于是 `IsSourceReliable` 返回 true，+12 照加，`result.Warn(...)` 那条本该出现的警告也永远不会出现。

也就是说：**真正需要修的是采集器的上报，不是这道闸门**。

建议（Core 0.2，与计划任务那条同类）：让进程采集器在"有进程枚举失败/无权限打开"时报 `Partial`，例如：

```
Source: 运行中的进程
Status: Partial
ItemsScanned: 193   ItemsFailed: 163   ItemsCollected: 193
Error: 部分进程无权限访问（当前未提权，建议以管理员身份运行）
```

闸门一旦生效，收益是双份的：

1. `NoRunningProcess(+12)` 不再被错误加上 —— 这是根治，比 UI 禁用按钮有效得多；
2. UI 的健康度面板会自动显示「运行中的进程 · 未完成 · 193 条 · 部分进程无权限访问」，提示精确到来源，不再是笼统的"可能不完整"。

在那之前，UI 侧的禁用 + 额外确认只是缓解。
