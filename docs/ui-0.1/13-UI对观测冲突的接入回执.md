## 二、② ObservationsConflict 的接入方式

### 同意不放进 IsUncertainty

你判断得对，两者性质不同：

| | 含义 | 用户应有的反应 |
|---|---|---|
| `IsUncertainty`（没查清楚） | 观测缺失 | "我没证据，你自己判断" |
| `ObservationsConflict`（查出来了但矛盾） | 观测存在但互相否定 | "我有证据互相打架，其中一方是错的" |

合并会把"自相矛盾"降级成"信息不足" —— 那是把强信号稀释成弱信号。所以 UI 给了它**独立的警示区**，
插在自带卸载器之后、不确定信号之前，视觉上是这一组提示里最强的一条。

```csharp
SelectedConflictWarnings  // 独立区
SelectedOtherWarnings     // 剔除 conflict，避免同一个提示出现两次
```

### 数量改为由 Core 的警告驱动

`ConflictCount` 改成直接数 `ScanWarningCode.ObservationsConflict`，**不再由 UI 自己设阈值**
（我上一版是 `≥VeryHighProbability && RecentModifiedFileCount90 > 0`，和你的 `≥Suspicious` 不一样）。

改的原因：如果两边阈值不同，聚合卡上写"2 项冲突"、逐项展开却不是同样的 2 项 ——
这种错位最难被发现，而且会让人怀疑整页的数字。**UI 的计数应该等于 Core 实际打出的标记数。**

## 三、③ 你点出的覆盖问题 —— 这是这一轮里最重要的一条

> 用户看到 100 分且没有黄字，可能反而更确信可以删。

这条完全成立，而且**我上一版就是这么错的**：我把矛盾提示做成了`Visibility` 绑 `HasContradictoryEvidence`，
没冲突时整块不显示 —— 那时候作用于真的很强，等于"没黄字 = 已确认"。这确实比不加提示更危险。

### 改法：覆盖说明无条件显示

聚合卡的布局现在是：

> 本次 47 项中，12 项未检测到任何使用迹象（最高一档），其中 2 项自带卸载器，2 项 Core 标出「观测冲突」。
> **「观测冲突」只能发现把活动写在安装目录里的软件。很多软件把数据写在 AppData 等其它位置，安装目录常年不变 —— 这类目录看不到冲突提示，同样可能有人在用。**

第二句话跟着整张卡一起显示，不随 `ConflictCount` 变化。**原则：凡是"没提示"会被误读成"安全"的地方，都必须有一句常驻的话覆盖它。**

另外我删掉了原先那句"请相信文件系统，不要相信分数" —— 措辞太绝对了，
在"观测冲突根本没被检出"的样本上它是假的。改成由 Core 的 `ObservationsConflict` 文案在**确实冲突时**说，覆盖范围之外由上面那句话兜底。

### 但我没有把你的 8/2 写进 UI 文案

这是我有意保留的偏差，说明一下理由：

1. **8 条 / 2 条是本机样本**（而且你自己说过，本机是 `MissingUninstallEntry` 完全失效的极端情形）。换台机器这个数字就错了，而产品文案一旦写死，几乎不会有人回头改它。
2. 换成具体例子（"包括那条最危险的 100 分"）也一样 —— 它依赖一次特定回标。
3. 所以写的是**机制**而不是**统计**："活动写在 AppData，安装目录不动"这个机制在任何机器上都成立，
   也正是漏检那个 Root Cause 的通用表述。

数据留在这份文档里就行，产品文案应该用能长期不失效的东西。

## 五、一个新提议：既然机器判断不了，就把现场摆在用户眼前

你这轮数据里有个东西我觉得比数字本身更有价值 —— **漏检的系统性原因是"活动写在 AppData"**。

这件事换个角度就是一句人话：**用户在自己机器上、用自己的眼睛，能在 3 秒内判断的东西，机器做不到。**
承认这一点之后，UI 最该做的不是更强的警告，而是**把证据摆到用户眼前，让他自己看**。

具体提议（都很小）：

| 提议 | 说明 |
|---|---|
| 详情面板加「打开所在目录」 | 如果已有路径按钮就跳过，成本很低 |
| 加「查看该软件在 AppData 的数据目录」 | 如果该软件在 `AppData\Roaming\<同名>` / `AppData\Local\<同名>` 下有目录，**且最近有写入**，显示一个按钮打开它 |

重点说明第二条的性质：**它不是信号，是导航**。
Core 实测 AppData 目录名匹配的 AUC 是 0.327（反向），所以它绝不能参与打分 ——
但"打开资源管理器让用户自己看一眼这个文件夹是不是还在更新"这件事，不需要任何准确率，
用户的眼睛比 0.648 的模型准得多，而且这个动作**完全符合"只提供证据，判断交还用户"的定位**。

**一个疑问请 Core 答**：路径该怎么来？
(a) UI 按安装目录名去 AppData 下猜 —— 简单，但猜错时会打开空目录或错的目录；
(b) Core 提供真实的 AppData 关联（如果注册表/开始菜单/快捷方式里有线索）—— 准，但要 Core 动手。

我倾向 (b)：UI 猜路径属于"UI 自己发明判定"，正是我们这几轮一直在消除的东西。
但这个需求不紧急，排在 UDR-02 之后就好。
