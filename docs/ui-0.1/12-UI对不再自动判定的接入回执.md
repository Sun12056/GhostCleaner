## 一、Q1：卸载器入口用的是完整路径 —— 确认，但 Core 侧有个坑

### UI 侧：三处都是完整路径，没有任何文件名比较

```csharp
// ViewModels/OrphanScanViewModel.cs
public bool SelectedHasUninstaller =>
    SelectedItem is { HasUninstaller: true } item
    && !string.IsNullOrEmpty(item.UninstallerPath)
    && File.Exists(item.UninstallerPath);          // ① 完整路径

private void RunUninstaller()
{
    if (SelectedItem?.UninstallerPath == null || !File.Exists(SelectedItem.UninstallerPath)) return;
    Process.Start(new ProcessStartInfo(SelectedItem.UninstallerPath) { UseShellExecute = true });  // ② 完整路径启动
    _log.Info("Clean", "RunUninstaller", "启动卸载程序：" + SelectedItem.UninstallerPath, ...);     // ③ 日志记完整路径
}
```

全项目唯一用到 `Path.GetFileName` 的地方是隔离区列表的"名称"列（`Converters.cs:460`），纯展示，
不参与任何识别判断。**这条你可以放心。**

### ⚠️ 但 Core 侧还有一处会把它写回 UI —— 而且正是通用名形态

你点名提醒我别用文件名判断。问题是：**UI 上用户读到的那句话本身就是 Core 用文件名拼出来的。**

```
EvidenceCollector.cs:111  →  Description = "目录包含 " + Path.GetFileName(UninstallerPath)
```

渲染到 UI 的"其它提示"区块就是：

> 目录包含 Uninstall.exe

按你给的实测，`UNINSTALL.EXE` 在 wangyiyunyinyue / IROK / aDrive / CloudMusic / ZWCAD2026
五个目录里都同名存在。用户看到五条一模一样的"目录包含 Uninstall.exe"，
很可能因此以为"这是同一个东西"，或者反过来以为"这就是那个软件的卸载器"。

**建议**：Description 里带上父目录名或完整路径：

```
目录包含卸载程序：D:\wangyiyunyinyue\Uninstall.exe
```

长度上完全能接受（这本来就是详情面板里的长文本区）。Core 改文案不需要 UI 配合 ——
结构化之后我这边不再做任何字符串匹配。

## 二、Q2：聚合提示已加，但加了一层你没写的交叉维度

你提议的句子我原样实现了，放在三张计数卡所在的「在看待置信度之前，先看这几点」区块顶部：

> 本次 47 项中，12 项未检测到任何使用迹象（最高一档）；其中 2 项自带卸载器；另有 5 项近 90 天仍有文件活动。

注意最后半句 —— **这是我擅自加的，理由如下**：

`N / M / K` 这组数字里，M（未检测到使用迹象）和 K（自带卸载器）是同一方向的：它们都指向"可以清理"。
真正能改变用户决定的信息是 **M ∩ 近 90 天有文件活动**，因为那是一组**互相矛盾的观测**：

- Core 的分数说"没人用它"
- 文件系统说"它昨天还在写文件"

而 Core 自己的回标数据已经回答了这种情况下该信谁 —— 47 条里 Precision 0.333，
96 分的网易云音乐天天在用。**有矛盾时应该信文件系统。**

所以这一条出现时，下面会紧跟一行黄字：

> 这 5 项同时具备两个互相矛盾的观测：分数最高，但近期确实有文件被修改。Core 47 条回标 Precision 只有 0.333 —— 这种情况下请相信文件系统，不要相信分数。

新增的 VM 属性（全部是聚合，无任何新判定逻辑）：

```csharp
VeryHighProbabilityCount                  // ≥90 分档
StrongDetectionWithRecentActivityCount    // ≥90 且 RecentModifiedFileCount90 > 0  ← 矛盾项
StrongDetectionUninstallerCount           // ≥90 且 HasUninstaller
HasContradictoryEvidence                  // 矛盾项 > 0
StrongDetectionGroupText                  // 上面那句话
```

**一条建议**：这条矛盾项将来可以考虑由 Core 直接产出（某种"观测冲突"标记），
因为它把"分数 + 文件系统"两条独立信息合起来判断，而不是单点证据 ——
这恰好是"只提供证据"定位下 Core 可以合理做的、UI 不该自己发明的东西。
UI 现在做的是纯集合交集，不涉及权重，先这样跑着。

## 三、Registry Repair 这个反例，值得单独说

```
Registry Repair   真值=残留   置信=96   Prefetch=2026-10-16（昨天）
```

这条数据比 AUC 0.620 本身更有说服力：**它是唯一两条判对样本里分数最高的那条**，
而落地"近期运行过 = 在用"会把它翻成误报，Recall 掉一半。

它说明的不是 Prefetch 不好，而是**"近期运行过"这个命题在本机上天然不可信** ——
残留软件的卸载器会被扫描、被触碰、被调用一次清理逻辑，就留下一条"运行"记录。
任何依赖"可执行文件被调用过"的信号都会踩这个坑，Prefetch 只是第一个试出来的。

所以对 UI 的影响是确定的：**我不会因为某个信号"看起来能证实在用"就降低闸门级别**。
分级顺序保持不动：

```
未提权 → 90 天活动 → 自带卸载器 → 高风险 → 受保护 → 确认
```

## 五、跨时间观测：UI 可以先做个原型，要不要？

你说唯一可能有解的方向是 v0.2 的跨时间观测。**这个方向 UI 现在就能动，而且不用 Core 先做。**

原因：UI 层已经有一个每次扫描写一次的快照（`UiStateService` / `ui.json`，
UDR-02 落地前由 UI 临时持有）。如果我在这个快照里额外记每个检出目录的：

```
Path · SizeBytes · RecentModifiedFileCount90 · MaxLastWriteTime · 本次扫描时间
```

那么第二次扫描时 UI 就能自己算出这些：

| 指标 | 含义 |
|---|---|
| SizeBytes 增长 | 还在被写入（缓存/数据目录的典型特征） |
| MaxLastWriteTime 前移 | 有新写入 —— 强于任何"运行过"信号，因为它不会在卸载时被触碰 |
| RecentModifiedFileCount90 变化 | 活跃度趋势 |
| 连续 N 次扫描无任何变化 | 弱证据，但**多个独立观测同时静止**这件事本身有区分度 |

这条路的好处是：**不需要 Core 判定，纯观测，和"只提供证据"的定位完全一致**。风险也有：
风险也很明确：多个快照的时间跨度要够长才有意义，第一次扫描得不到任何结论，
UI 必须明说"仅首次扫描，暂无趋势"，否则用户会把它误读成"这软件没变化 = 没人用"。

**要不要做由你定。** 我倾向于不先接 `ui.json`，而是让它归入 UDR-02 由 Core 正式产出 ——
否则等 Core 真正实现时，UI 这边又要迁移一次。排期参考：UI 原型大约一个工作日，且不占用 Core 的工作量。
Core 没定之前我不动它。
