## 零、先说结论

接受"以 Core 判定不可靠为前提设计 UI"。三条 P0 全部落地。

我理解这件事的性质：**这不是精度不够，是特征在当前场景下没有区分度**。
系统重装后「完整软件特征 + 缺失全部关联」在本机上等价于"重装后仍在用的软件"。
所以 UI 侧的做法不是"把话说委婉一点"，而是**把置信度降级为一类次要信息**，让真正有价值的观测（近期文件活动、自带卸载器、检查未完成）排在它前面。

### 2. 两类 warning 已展示

### 3. 闸门保留，且加强（同意不放宽）

`CleanAsync` 现在按这个顺序拦：

```
1. 未提权闸门（永久删除禁用 / 其余额外勾选确认）      ← 已存在
2. 近 90 天仍有文件活动                              ← 新增
3. 自带卸载器                                        ← 新增
4. 高风险
5. 受保护内容（可恢复才允许）
6. 常规 / 永久删除确认
```

新增的第 2 步：

> 本次选中的 N 项中，有 M 项近 90 天内有文件被修改。
> 这些目录很可能仍在使用。删除前请确认它们确实不再需要，
> 尤其是系统重装后 D 盘遗留的目录 —— 它们往往正是还在用的软件。
> ☐ 我已知悉其中有目录近期仍有文件活动，仍要对全部选中项继续

新增的第 3 步（对应 Core「从不输出 Quarantine」）：

> 本次选中的 N 项中，有 K 项自带卸载程序：…
> Core 不会对这些目录建议隔离。直接删除目录会绕过正规卸载流程，残留注册表项、服务与系统关联。
> 更安全的做法：取消勾选它们，然后在详情面板点「运行自带卸载器」。
> ☐ 我已知悉存在更安全的卸载方式，仍要直接处理整个目录

## 二、答复你的两个问题

### 问题 1：使用自带卸载器入口可行吗？要不要补字段？

**可行，而且不用补字段 —— 已经有了。**

```
OrphanItem.UninstallerPath    src/WinCleaner.Core/Models/OrphanItem.cs:38
OrphanItem.HasUninstaller     :36
软件目录探测赋值               Scanner/SoftwareDirectoryInspector.cs:182
写入 OrphanItem               Scanner/RiskEvaluator.cs:87
```

`RiskEvaluator` 已经在把 `info.UninstallerPath` 写到 `OrphanItem` 上。UI 侧在列表行、详情面板、批量闸门三处都已接上。

**请 Core 顺手确认两件事**：
1. 你们两轮真机数据里 `UninstallerPath` 是否都有值？（UI 已用 `File.Exists` 兜底，路径不可执行时不显示按钮）
2. `EvidenceCollector.cs:111` 那条卸载器证据的 Description 是 `Path.GetFileName(UninstallerPath)`，如果 `UninstallerPath` 为 null 会写成空串 —— 与 `HasUninstaller` 为 true 矛盾时会很难查。建议加个防御。

### 问题 2：愿意加「M 项近 90 天有文件活动」的提示吗？

**愿意，已加，而且不需要新字段。**

UI 用 `EvidenceType.RecentFileActivity` 聚合（枚举匹配，不是字符串匹配）：

```csharp
public int RecentActivityCount =>
    Results.Count(x => x.Evidence.Any(e => e.Type == EvidenceType.RecentFileActivity));
```

三处呈现：
- 结果页顶部：三个并排计数卡（近 90 天有文件活动 / 自带卸载器 / 未能确认是否正在运行），标题是「**在看待置信度之前，先看这几点**」
- 列表行：「近期有活动」黄底徽标（比任何置信度分数都先入眼）
- 批量清理闸门（上面的第 2 步）

**仍然建议**把 `RecentModifiedFileCount90` 挂到 `OrphanItem` 上。理由：现在只能说"有/没有"，挂上之后能说"近 90 天修改了 X 个文件" —— 文件数是量级信息，用户判断"还在用吗"时比布尔值有用得多（微信那条第 100 个文件 vs 1 个文件，含义完全不同）。

## 三、反过来要请 Core 看的三件事

### 1. Warning 需要结构化（Code + Message）

UI 现在只能按文案匹配把 warning 分成"不确定"和"其它提示"：

```csharp
// ViewModels/OrphanScanViewModel.cs
private static bool IsUncertaintyWarning(string warning)
    => warning.Contains("未能完成") || warning.Contains("可能不完整") || warning.Contains("检查未完成");
```

这很脆 —— Core 改动措辞、加句号、换同义词都会静默失效，而且失效是"提示消失"而不是报错，最难发现。

建议：`EvidenceCollection` / `RiskEvaluator` 输出带类型的对象：

```csharp
public readonly record struct ScanWarning(string Code, string Message);
// Code 例：AssociationIncomplete / ProcessCheckIncomplete / HasUninstaller / GameDirectory
```

UI 侧改成 `switch (warning.Code)`，一行都不影响现有文案。

### 2. 导出报告里的措辞与 UI 已经不一致了

`ReportExporter.cs:58,113` 写的是 `item.ConfidenceLevelText`，源头仍是 Core 的：

```csharp
OrphanConfidenceThresholds.ToText  →  "非常高概率残留" / "高概率残留" / "可疑" / "普通"
```

也就是说**导出的 JSON/CSV 报告还在用结论式措辞**，而 UI 已经改成"未检测到使用迹象"。同一份数据两种说法，用户会困惑，也违背这次整改的目的。

建议 Core 把 `ToText` 改成（或新增一份展示用文案）：

```
VeryHighProbability → "未检测到任何使用迹象"
HighProbability     → "几乎未检测到使用迹象"
Suspicious          → "使用迹象较少"
Normal              → "检测到使用迹象"
```

字段名（`VeryHighProbability` 等）不用动，我也不建议动 —— 它描述的是证据等级，语义没问
题，问题只在展示文案。另外报告里最好再带一句 caps 说明，否则读报告的人不知道 96 分该怎么看。

### 3. 既然 0/47 输出 Quarantine，是否索性不输出 Quarantine？

现在 `RiskEvaluator.Recommend` 里唯一能输出 `Quarantine` 的分支是
`VeryHighProbability && risk == RiskLevel.Low`，而实测是 0/47 ——
自带卸载器的目录在 `Recommend` 第 213 行就被提前返回 `Review`，把这条路堵掉了大半。以 AUC 0.648 为前提，这条分支幸存的概率空间很小，但它一旦命中，UI 就会显示"推荐操作：隔离"，那是我们最不想让用户盲信的一句话。

我的建议：**把最后那个 `Quarantine` 也降为 `Review`，让 Core 的建议集合收敛到 `{Keep, Review, HighRiskReview}`**，"隔离"永远只是一个用户可以自己选择的动作，不由 Core 建议（之前已有的讲法）。
这也让你正在考虑的"只提供证据，不做自动判定"在代码层面先落地一半，不用等 Prefetch 的结论。

要不要做由 Core 定；UI 侧两种都能显示（详情面板的推荐操作条直接绑 `RecommendationText`），改起来是零成本。

## 五、Prefetch 那段的一个提醒

如果 Prefetch 走的是"按 exe 名精确匹配"，它大概率也会命中同一个陷阱：
重装过的机器上，用户天天在用网易云音乐，Prefetch 里**会有**它的记录 —— 于是这条信号会把
96 分那条拉下来，这正是你想要的。
但同时，真正被废弃的软件在重装前跑过，Prefetch 记录可能也在（取决于磁盘重装是否格式化）。
所以它改善的可能主要是"仍在使用"侧的 Recall，而不一定提升"区分度"。

建议验证时不要只看总 AUC，把 **96 分那 4 条各自的分数变化** 单独列出来 —— 它们是这次的核心用例。
如果 Prefetch 能把这 4 条压到 `Keep` 或 `Review` 区间，比 AUC 涨 0.05 更有说服力。
